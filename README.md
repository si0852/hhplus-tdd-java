# 동시성 제어 방식에 대한 분석 및 보고서 작성
_______
### [목적]
>분산환경이 아닌 상황에서 동시성 문제를 정리하고, 적합한 동시성 제어 방식을 선정한다. 
_________
## 동시성 의미
- 동시성은 여러 사용자의 요청이 시간상 겹쳐 실행되면서, 동일한 데이터 또는 리소스에 동시에 접근하는 상황

________
## 포인트 시스템 동시성 시나리오
1. 동일 유저 동시 충전
    #### 한 유저가 여러 디바이스에서 동시에 충전
    ```
    - 모바일에서 1000원 충전
    - 웹에서 2000원 충전
    - 태블릿에서 3500원 충전
    
    - 기대 결과: 6500원 증가 -> 최종 잔액 6500원
    - 위험 : Race Condition
        - 마지막 요청(3500원)만 반영되어 3500원만 증가
        - 일부 충전 내역이 잔액에 반영 X
    ```

2. 동일 유저 동시 사용 
   #### 결제 중복 클릭, API 재시도
   ```
   - 현재 잔액 5000원
   - 3000원 사용 요청 3번 동시 발생
   
   - 기대 결과: 1번만 성공, 2번은 실패 또는 잔액 부족
   - 위험
      - 중복 차감 -> 음수 포인트 발생 가능
      - 사용 이력은 3건인데 실제 잔액은 그에 맞게 차감되지 않는 불일치 가능
   ```

3. 충전과 사용 동시 발생
   #### 충전 처리 중 사용 요청
   ```
   - Thread 1: 10000원 충전
   - Thread 2: 3000원 사용 (동시)
   
   - 기대 결과
        - 충전 -> 사용 순서로 처리, 최종 잔액 7000원
        - 사용 -> 충전 순서로 처리
            - 잔액 0원에서 3000원 사용 요청 -> 잔액 부족으로 실패
            - 이후 10000원 충전 -> 최종 잔액 10000원
   - 위험
        - 하나의 연산이 다른 연산을 덮어써 기록 누락
        - 충전은 되었는데 사용 이력만 남거나, 반대로 사용만 반영되고 충전이 누락되는 정합성 문제
   ```

4. 여러 유저 동시 처리 (격리 테스트)
   #### 유저 A,B의 작업이 서로 영향 주는지 확인
   ```
    - 유저 A: 충전 100번
    - 유저 B: 충전 100번 (동시)
   
    - 기대 결과
         - A의 충전 100건, B의 충전 100건이 각각 정확하게 처리
         - A와 B의 포인트는 서로 영향을 주지 않고 독립적으로 유지
    - 위험
         - Global Lock 사용 시 모든 유저의 충전 요청이 직력화되어 성능 저하
         - 유저 간 격리는 보장되지만, 불필요한 병목 지점이 생길 수 있음
   ```

5. 잔액 부족 상황 동시 사용
   #### 잔액이 충분하지 않은 상태에서 동시 사용
   ```
    - 현재 잔액 1000원
    - 800원 사용 요청 3번 동시 발생
   
    - 기대 결과: 1번 성공, 나머지 실패
    - 위험
         - 여러 요청이 동시에 통과하여 잔액이 음수가 될 수 있음
         - 실제 사용 가능 금액(1000원)을 초과하는 사용 이력이 생성될 수 있음
   ```

## 시나리오별 동시성 제어방식
1. 한 유저가 여러 디바이스에서 동시에 충전 -> 모든 충전 요청이 잃어버림 없이 누적
   > synchronized/ReentrantLock 적합
   - 잔액 조회 -> 증가 DB 업데이트 -> 이력 기록 전체를 하나의 섹션으로 묶어 순차 실행
   - 동일 유저의 충전 요청은 직렬화되므로 Race Condition 방지
   - 다른 유저는 서로 다른 락을 쓰므로 병렬 처리 가능

2. 동일 유저 동시 사용(결제 중복 클릭)
   > synchronized/ReentrantLock 적합
   - 잔액조회 -> 검증 -> 차감 -> 이력 전체를 하나의 섹션으로 묶어 순차 실행
   - 다른 유저는 서로 다른 락을 쓰므로 병렬 처리 가능

3. 충전과 사용 동시 발생
   > synchronized/ReentrantLock 적합
   - 순서에 따라 결과는 다를 수 있지만, 항상 일관된 상태 유지
   - 한 유저의 포인트 변경은 항상 순차 실행 보장

4. 여러 유저 동시 처리(격리 테스트)
   > synchronized/ReentrantLock 적합
   - 동일 유저에 대해서만 직렬화, 서로 다른 유저끼리는 병행 수행

5. 잔액 부족 상황 동시 사용
   > synchronized/ReentrantLock 적합
   - 포인트 사용 영역은 정합성 > 성능이 우선이므로 synchronized/ReentrantLock 적합 
________
### synchronized vs ReentrantLock 비교 결과(SynchronizedVsReentrantLockTest)
- [synchronized] 성공: 100, 실패: 0, 소요시간: 41886ms, 최종포인트: 10000 (예상: 10000)
- [ReentrantLock(Unfair)] 성공: 100, 실패: 0, 소요시간: 39928ms, 최종포인트: 10000 (예상: 10000)
- [ReentrantLock(Fair)] 성공: 100, 실패: 0, 소요시간: 42375ms, 최종포인트: 10000 (예상: 10000)
> 위 결과를 통해 세 가지 방식 정합성 측면에서는 예상 포인트와 최종 포인트가 일치하여 동시성 제어가 올바르게 동작함을 확인

> 성능 측면에서는 해당 테스트 환경에서
**ReentrantLock(Unfair)** 이 `synchronized` 대비 약간 더 짧은 소요 시간을 보였고,
공정 락인 **ReentrantLock(Fair)** 은 대기 큐 순서를 보장하는 대신
`synchronized`보다 약간 더 느리게 측정되었다.

> 정합성 요구사항을 만족하는 가정하에 더 나은 성능을 보이는 ReentrantLock(Unfair)를 동시성 제어방식이 적합하다고 판된되어 선택을 하였다.
